name: design-review
description: "게임 기획서의 완성도, 내부 일관성, 구현 가능성, 프로젝트 기획 표준 준수 여부를 검토합니다. 기획서를 프로그래머에게 전달하기 전에 실행하세요."
argument-hint: "[기획서-경로]"
user-invocable: true
allowed-tools: Read, Glob, Grep
---
이 스킬이 실행되면:
1. **대상 기획서를 전체** 읽는다.
2. **프로젝트 지침 문서(`CLAUDE.md` 또는 `AGENTS.md`)를 읽어** 프로젝트 컨텍스트와 표준을 파악한다.
3. **대상 문서에서 참조하거나 암시하는 관련 기획서를 읽는다**
   (기획서 폴더 — 예: `design/gdd/` — 에서 관련 시스템 문서 확인).
4. **기획서 표준 체크리스트에 따라 평가한다**:
   - [ ] 개요 섹션 있음 (한 문단 요약)
   - [ ] 플레이어 판타지 섹션 있음 (의도된 플레이 감각)
   - [ ] 세부 규칙 섹션 있음 (모호하지 않은 메커니즘)
   - [ ] 공식 섹션 있음 (변수와 함께 모든 수식 정의)
   - [ ] 엣지 케이스 섹션 있음 (특수 상황 처리)
   - [ ] 의존성 섹션 있음 (관련 타 시스템 목록)
   - [ ] 튜닝 파라미터 섹션 있음 (설정 가능한 값 식별)
   - [ ] 수용 기준 섹션 있음 (테스트 가능한 성공 조건)
5. **내부 일관성을 점검한다**:
   - 공식이 설명된 동작과 일치하는 값을 산출하는가?
   - 엣지 케이스가 주요 규칙과 모순되지 않는가?
   - 의존성이 양방향으로 명시되어 있는가? (상대 시스템도 이 시스템을 인지하고 있는가?)
6. **구현 가능성을 점검한다**:
   - 프로그래머가 추측 없이 구현할 수 있을 만큼 규칙이 명확한가?
   - 세부 사항이 누락된 "두루뭉술한" 섹션이 있는가?
   - 성능 영향에 대한 고려가 있는가?
7. **시스템 간 일관성을 점검한다**:
   - 기존 메커니즘과 충돌하는 부분이 있는가?
   - 다른 시스템과 의도치 않은 상호작용이 발생하는가?
   - 게임의 확립된 톤 및 핵심 원칙과 일치하는가?
8. **다음 형식으로 리뷰를 출력한다**:
```
## 기획 검토: [문서 제목]
### 완성도: [8개 섹션 중 X개 존재]
[누락된 섹션 목록]
### 일관성 문제
[내부 또는 시스템 간 모순 목록]
### 구현 가능성 우려 사항
[모호하거나 구현 불가능한 섹션 목록]
### 밸런스 우려 사항
[명백한 밸런스 위험 목록]
### 권고 사항
[우선순위가 정해진 개선 사항 목록]
### 판정: [승인 / 수정 필요 / 대폭 수정 필요]
```
9. **상황에 맞는 다음 단계를 권고한다**:
   - 검토 대상 문서가 `game-concept.md` 또는 `game-pillars.md`인 경우:
     - `design/gdd/systems-index.md`가 존재하는지 확인
     - 존재하지 않으면 권고 사항에 다음을 추가:
       > "이 컨셉은 시스템 분해 단계로 넘어갈 준비가 되었습니다. `/map-systems`를
       > 실행하여 의존성과 우선순위가 포함된 개별 시스템으로 분해한 후,
       > 시스템별 GDD를 작성하세요."
   - 검토 대상 문서가 개별 시스템 GDD인 경우:
     - 시스템 인덱스가 해당 시스템을 참조하는지 확인
     - 판정이 **승인**이면: "시스템 인덱스에서 이 시스템의 상태를 '승인됨'으로
       업데이트하세요."를 제안
     - 판정이 **수정 필요** 또는 **대폭 수정 필요**이면: "시스템 인덱스에서 이 시스템의
       상태를 '검토 중'으로 업데이트하세요."를 제안
     - 참고: 이 스킬은 읽기 전용입니다. 실제 시스템 인덱스 상태 업데이트는
       사용자(또는 `/design-system`)가 직접 수행해야 합니다.
