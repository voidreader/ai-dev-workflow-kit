## Flutter 개발 원칙

- 프로젝트의 기존 아키텍처, 상태 관리, 데이터 계층, 명명 규칙을 먼저 확인하고 따른다.
- 기능과 버그 수정은 테스트 우선으로 진행하고 완료 전 `flutter analyze`와 관련 테스트를 실행한다.
- 생성 코드가 관련되면 프로젝트가 지정한 `build_runner` 명령을 실행하고 생성 결과를 함께 검증한다.
- 사용자 지시와 이 프로젝트의 더 구체적인 규칙이 이 문서보다 우선한다.

## Superpowers 사용

- 요구사항이나 설계가 불명확하면 `superpowers:brainstorming`으로 계약을 먼저 확정한다.
- 여러 단계의 구현은 `superpowers:writing-plans`, 기능과 버그 수정은 `superpowers:test-driven-development`, 예상 밖 실패는 `superpowers:systematic-debugging`을 사용한다.
- 완료를 주장하기 전에 `superpowers:verification-before-completion`의 검증 원칙을 따른다.
- Superpowers를 사용한다는 이유만으로 모든 작업에 subagent나 전체 계획 재독을 적용하지 않는다. 아래 위험 등급으로 실행 방식을 정한다.

## 작업 등급

경계가 모호하면 한 단계 높인다.

### 경량

다음 조건을 모두 만족할 때만 경량으로 처리한다.

- 변경 파일이 1~2개이고 코드 변경이 대략 100줄 이내다.
- 공개 API·함수 시그니처·공용 모델을 바꾸지 않는다.
- DB·로컬 저장소·동기화·마이그레이션을 건드리지 않는다.
- 비동기 생명주기·경쟁 상태·권한·결제·광고·플랫폼 채널을 건드리지 않는다.
- 아키텍처 판단 없이 기존 패턴을 따르며 검증 방법이 명확하다.

메인 에이전트가 직접 구현한다. subagent는 사용하지 않되 관련 테스트와 자체 diff 검토는 수행한다.

### 표준

한 기능 영역의 3~8개 파일을 바꾸거나 경량 조건 하나라도 충족하지 못하면 표준으로 처리한다. 같은 마일스톤의 순차 의존 작업 2~3개는 가능하면 동일한 구현 에이전트가 맡는다. 마일스톤 종료 시 통합 검토한다.

### 고위험

DB·동기화·보안·결제·플랫폼 채널·동시성·대규모 공개 인터페이스 변경은 고위험이다. 독립적인 논리 슬라이스로 나누고 슬라이스 검토와 최종 통합 검토를 수행한다.

## 마일스톤 brief

구현 에이전트에는 전체 계획 대신 현재 마일스톤 brief를 제공한다. brief의 필수 항목은 다음과 같다.

- 목표와 관련 요구사항
- 전역 불변조건과 금지사항
- 수정 대상 파일과 읽어야 할 관련 파일
- 선행 작업의 인터페이스·데이터 계약
- 범위 밖 항목
- 수용 기준과 실행할 테스트
- 원본 계획 경로와 관련 절·태스크 번호

brief를 기본 계약으로 사용한다. 모호함, 계약 충돌, 예상 밖 결합이 발견될 때만 원본 계획의 관련 절로 확장한다. 마일스톤 책임자는 brief가 원본 요구사항과 불변조건을 보존하는지 확인한다.

## 리뷰 패키지

리뷰 전에 다음 전체 변경 인벤토리를 확인한다.

- `git diff --stat`과 변경 파일 전체 목록
- 계획 밖 파일과 생성 코드 변경 여부
- 공개 시그니처·모델·스키마·마이그레이션 변경
- 추가·수정·실행한 테스트 목록

상세 리뷰는 요구사항과 직접 관련된 파일·hunk부터 시작한다. 공개 API, Provider·Notifier, 스키마·마이그레이션, outbox·snapshot·sync·hydration, 플랫폼 생명주기, 동시성, 생성 코드, 계획 밖 파일, 예상보다 큰 diff가 보이면 인접 호출부와 전체 diff로 범위를 넓힌다. 관련 hunk만 보고 전체 변경을 승인하지 않는다.

## 수정 라운드

같은 결함 또는 같은 수용 기준 실패에 대한 자동 수정은 최대 2회다.

1. 1차는 원인을 좁혀 최소 수정하고 집중 테스트를 실행한다.
2. 2차는 근본 원인과 누락된 회귀 테스트를 확인한 뒤 수정한다.

2차 이후에도 실패하면 자동 수정 루프를 중단하고 전략 변경 게이트를 연다. 로그와 가정을 다시 검토한 뒤 작업 분할, 설계 수정, 모델 상향 또는 사용자 판단 중 하나를 선택한다. 해결되지 않은 치명적 문제를 승인하거나 같은 문제를 새 라운드로 위장하지 않는다.

## 테스트와 출력

- 구현 중에는 집중 테스트를 실행한다.
- 핵심 스모크 테스트는 2~3개 작업마다 실행한다.
- 전체 회귀는 3~5개 작업, 기능 마일스톤 종료, 영향 범위가 큰 변경 직후, 완료 직전에 실행한다.
- 성공 로그는 테스트 수·성공 여부·소요 시간으로 요약한다. 실패 시 실패한 테스트와 직접 관련된 스택만 확장한다.
